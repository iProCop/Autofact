## 1. Временной интервал (freshness)

### Вопрос

Стоит ли добавить временной интервал: если мнения экспертов слишком старые — платформенного балла нет, даже если осмотров ≥ 3, но один из них «протух»?

### Ответ

**Да, для продукта это логично**, но **не в уроке 8**.

Осмотр трёхлетней давности и вчерашний — это часто уже **разная машина** (пробег, ДТП, ремонт). Сводный балл «по VIN» без учёта свежести может вводить клиента в заблуждение.

**Когда внедрять:** урок 9 (Reports), когда в данных есть `publishedAt` / `inspectedAt`.

### Варианты политики

| Подход | Суть | Плюсы | Минусы |
|--------|------|-------|--------|
| **Жёсткий cutoff** | Учитываем только осмотры за последние N дней (например 180) | Просто объяснить клиенту | Резко: вчера было 3, сегодня — 2 |
| **Мягкий decay** | Старые осмотры входят, но вес падает со временем | Плавнее | Сложнее в UI и тестах |
| **«3 свежих»** | Нужно ≥3 экспертов **и** все их осмотры не старше N дней | Честно: один старый «ломает» балл | Строго, мало данных на старте |

### Рекомендация для AutoInspect

На старте — **жёсткий cutoff 180 дней** (или 365 для самого первого MVP):

```
1. Фильтр: inspectedAt >= now - N days
2. uniqueByExpert по оставшимся
3. Если unique.length < 3 → platformScore: null
4. Иначе — текущая формула calculate()
```

**Про «один старый из трёх»:** после фильтра если остаётся < 3 уникальных экспертов — **`platformScore: null`**. Жёсткий cutoff честнее для клиента, чем «среднее по двум свежим».

### Поля ответа API (v2)

| Поле | Зачем |
|------|--------|
| `staleExcludedCount` | Сколько осмотров отбросили по возрасту |
| `oldestIncludedAt` | Насколько «старое» самое древнее учтённое мнение |
| `freshnessWindowDays` | Какое окно применили (прозрачность) |

### Реализация (эскиз)

```typescript
export type ExpertScoreInput = {
  expertId: string;
  overallScore: number;
  expertRating: number;
  inspectedAt: Date; // урок 9+
};

// Фильтр — снаружи calculate() или отдельный метод:
filterFresh(scores: ExpertScoreInput[], maxAgeDays = 180, now = new Date()): ExpertScoreInput[]
```

## 2. Приоритет эксперту с высоким рейтингом

### Вопрос

Как отдать приоритет оценке эксперту с более высоким рейтингом?

### Ответ (уже в MVP, урок 8)

**Взвешенное среднее по `expertRating`:**

```
w = max(expertRating, 0.1)
platformScore = round2( Σ(overallScore × w) / Σ(w) )
```

Эксперт с рейтингом **5.0** тянет итог сильнее, чем с **1.0**. Это **пропорциональный вес**, не «один главный эксперт».

Пример из теста: два слабых (rating 1, score 6) + звезда (rating 5, score 9) → итог **> 7.5**, ближе к 9.

### Если нужно усилить влияние топов (v2+)

| Усиление | Когда |
|----------|--------|
| **Квадрат веса** `w²` | Топ-эксперты должны доминировать сильнее |
| **Cap** `w = min(rating, 5)` | Звезда не задавливает всех полностью |
| **Time × rating** | `w = rating × freshnessFactor(inspectedAt)` — свежий топ важнее старого |
| **Отдельный «lead expert score»** | Другая фича, не platform score |

**Рекомендация MVP:** оставить **линейный вес** — просто, тестируемо, понятно в UI.

## 3. Последний осмотр эксперта vs первый

### Проблема

В уроке 8 `uniqueByExpert` берёт **первое** вхождение по `expertId`. Если один эксперт осмотрел машину дважды (старый + новый отчёт), в массив может попасть **устаревший** осмотр.

### Решение (урок 9+)

Перед `calculate()`:

- группировать по `expertId`;
- оставлять запись с **максимальным `inspectedAt`** (последний осмотр).

Урок 8 **не меняем** — там first-wins осознанно и покрыт тестом «один эксперт дважды не считается за двоих».

## 4. disputed и статус отчёта

### Как в эталоне (Reports)

При пересчёте по VIN (`recalculatePlatformScore`):

```typescript
const status = result.disputed ? ReportStatus.DISPUTED : ReportStatus.PUBLISHED;

await prisma.carReport.updateMany({
  where: { vin, status: { in: [PUBLISHED, DISPUTED] } },
  data: {
    platformScore: result.platformScore,
    status: result.platformScore === null ? ReportStatus.PUBLISHED : status,
  },
});
```

**`disputed` — не только флаг для UI**, а смена **`ReportStatus.DISPUTED`** на всех опубликованных отчётах этого VIN (когда балл посчитан).

Если `platformScore === null` (< 3 экспертов) — статус остаётся **PUBLISHED**, балла на карточке нет.

### Для solo

Подключится на **уроке 9**, не на уроке 8.

## 5. Два вида «нет платформенного балла» в UI

Клиенту важно различать ситуации:

| `platformScore` | `disputed` | `sampleSize` | Что показать |
|-----------------|------------|--------------|--------------|
| `null` | `false` | 0–2 | «Платформенный балл появится после 3 независимых осмотров (сейчас: N)» |
| `null` | `false` | после freshness-фильтра | «Недостаточно **свежих** осмотров» (v2) |
| число | `false` | ≥3 | «Платформа: **8.1**/10 на основе N осмотров» |
| число | `true` | ≥3 | «**≈ 7.2**, но эксперты **существенно расходятся**» + предупреждение |

`sampleSize` уже есть в `PlatformScoreResult` — использовать в каталоге и на странице отчёта (уроки 13–15).

## 6. Edge cases

| Случай | Ожидаемое поведение |
|--------|---------------------|
| `calculate([])` | `{ platformScore: null, disputed: false, sampleSize: 0 }` |
| Один `expertId` × N отчётов | Один голос после `uniqueByExpert` |
| `expertRating = 0` | Вес = 0.1 (`max(rating, 0.1)`) |
| Разброс ровно 2.0 | `disputed: false` (порог **строго** `> 2.0`) |
| `overallScore` вне 1–10 | MVP: не валидируем в сервисе; валидация на publish (Reports) |

Опциональный тест на пустой массив — по желанию, не блокер урока 8.
