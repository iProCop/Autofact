Назначение: Единый источник истины (Single Source of Truth) для генерации кода агентом Cursor.
1. СУТЬ ПРОЕКТА
Маркетплейс отчетов автоэкспертов по осмотру подержанных автомобилей. Платформа решает проблему географических ограничений и недоверия при покупке авто.
Эксперты проводят осмотр (фото/видео без госномеров), загружают отчеты.
Платформа автоматически рассчитывает итоговую оценку автомобиля на основе консенсуса 3-х и более независимых экспертов (модель "wisdom of the crowd").
Клиенты покупают готовые отчеты или заказывают индивидуальный выезд эксперта.
Модель: 1 осмотр эксперта может быть продан многократно, обеспечивая масштабируемый доход.
2. РОЛИ ПОЛЬЗОВАТЕЛЕЙ
CLIENT (Клиент): Ищет авто, покупает отчеты, заказывает выезд эксперта, покупает B2B-подписки или пакеты "Авто под ключ".
EXPERT (Эксперт): Создает профиль, загружает отчеты, получает частные заказы, выводит заработанные средства. Имеет публичный рейтинг.
ADMIN (Администратор): Модерирует экспертов и спорные отчеты, управляет комиссиями, видит всю аналитику платформы.
3. КЛЮЧЕВАЯ БИЗНЕС-ЛОГИКА (Правила для реализации)
3.1. Динамическое ценообразование (Pricing)
Цена отчета не хранится в БД как статичное число, а вычисляется на лету при запросе на основе даты создания (createdAt) и базовой цены (basePrice):
День 1–3: 100% от базовой цены.
День 4–10: 80% от базовой цены.
День 11–30: 50% от базовой цены.
День 31–60: 20% от базовой цены.
Более 60 дней: Статус "ARCHIVED", цена 0 (или скрыт из выдачи).
3.2. Алгоритм оценки платформы (Platform Scoring)
Если на один автомобиль (по VIN) есть 3 и более отчетов от разных экспертов:
Платформа рассчитывает средневзвешенную оценку. Вес оценки каждого эксперта пропорционален его личному рейтингу.
Если разброс оценок между экспертами превышает 20%, отчету автоматически присваивается статус DISPUTED (Спорный), и клиенту показывается предупреждение.
Если отчетов меньше 3, оценка платформы равна null, показывается только оценка конкретного эксперта.
3.3. Монетизация и транзакции
Платформа удерживает комиссию (15-25% для готовых отчетов, 20-30% для частных выездов) в момент успешной оплаты.
Остаток зачисляется на виртуальный баланс эксперта и доступен для вывода.
Реализовать защиту от повторной покупки: один клиент может купить один и тот же отчет только один раз.
4. ТЕХНИЧЕСКИЙ СТЕК (Строгие требования)
Backend: Node.js 20 LTS, NestJS, TypeScript (Strict Mode).
База данных: PostgreSQL.
ORM: Prisma (КАТЕГОРИЧЕСКИ НЕ ИСПОЛЬЗОВАТЬ TypeORM из-за проблем с типизацией и миграциями).
Кэш и очереди: Redis + BullMQ (для фоновых задач: сжатие видео, отправка уведомлений, пересчет цен).
Frontend (Mobile): React Native + Expo (Expo Router для навигации).
Frontend (Web): Next.js (App Router).
Хранилище: Yandex Object Storage (S3-compatible) + Yandex CDN.
Платежи: YooKassa (эквайринг, безопасная сделка, вебхуки).
Валидация: class-validator + zod для DTO.
5. СТРУКТУРА ДАННЫХ (Описание для генерации Prisma Schema)
Агент должен создать схему БД со следующими сущностями и связями:
User: Базовая сущность (email, пароль, роль: CLIENT/EXPERT/ADMIN). Связь 1-к-1 с профилем.
ExpertProfile: Привязан к User. Содержит: ФИО, регион, город, био, аватар, специализацию (массив), рейтинг (Decimal), счетчики осмотров и продаж, реквизиты для выплат.
ClientProfile: Привязан к User. Содержит: уровень B2B-подписки, дату окончания подписки.
CarReport: Основная сущность. Связь N-к-1 с ExpertProfile. Содержит: VIN (может быть скрыт), марку, модель, год, пробег, обязательные параметры для скоринга (оценка двигателя, кузова, салона, шин, электрики по шкале 1-5), базовую цену, статус (DRAFT, PUBLISHED, ARCHIVED, DISPUTED), вычисленные поля оценки платформы.
ReportMedia: Связь N-к-1 с CarReport (Cascade delete). Тип (PHOTO/VIDEO/DOC), URL в Yandex Storage, порядок сортировки.
CustomOrder: Заказ на выезд. Связь с ClientProfile и (после принятия) с ExpertProfile. Содержит ссылку на объявление, локацию, цену, статус (PENDING, ACCEPTED, IN_PROGRESS, COMPLETED, CANCELLED). При завершении создается связь с новым CarReport.
Transaction: Финансовая операция. Связь с User. Тип (PURCHASE, SALE, WITHDRAWAL, REFUND), сумма в копейках, ID платежа YooKassa, статус.
Purchase: Факт покупки отчета. Связь с ClientProfile и CarReport. Уникальное ограничение: один клиент + один отчет = одна запись. Хранит цену на момент покупки, комиссию платформы и выплату эксперту.
ExpertReview: Оценка эксперта клиентом после покупки/заказа (рейтинг 1-5, комментарий).
Требование к схеме: Обязательно добавить индексы на часто используемые поля поиска (регион, статус, дата создания, марка/модель).
6. АРХИТЕКТУРА API (REST)
Агент должен реализовать модули NestJS со следующими группами эндпоинтов:
Auth: Регистрация, логин (JWT), рефреш токена, логаут.
Users: Получение своего профиля, обновление данных, получение списка экспертов с фильтрацией по региону и рейтингу.
Reports: Создание черновика, загрузка медиа (через presigned URLs или multer), публикация, получение списка (с пагинацией и фильтрами), получение полного отчета (только после проверки права покупки).
Purchases: Инициация покупки (создает платеж YooKassa), получение истории покупок.
Orders: Создание частного заказа, получение списка заказов для эксперта, принятие/завершение заказа.
Payments: Вебхук от YooKassa для обновления статуса транзакции, запрос на вывод средств.
7. ПРАВИЛА РАБОТЫ ДЛЯ АГЕНТА CURSOR
Пошаговая генерация: Никогда не пытайся сгенерировать весь проект одной командой. Делай это модуль за модулем (сначала Prisma schema, затем Auth, затем Reports и т.д.).
Строгая типизация: Весь код должен быть на TypeScript со строгим режимом (strict: true). Избегай any.
Приоритет Prisma: При любых вопросах работы с БД используй синтаксис и подходы Prisma ORM. Не предлагай решения для TypeORM.
Безопасность: Все эндпоинты, кроме публичного каталога и авторизации, должны быть защищены Guards (JWT + Role Guard).
Обработка ошибок: Используй глобальные Exception Filters в NestJS. Возвращай понятные сообщения об ошибках с кодами HTTP.
Тестирование: Для критически важной бизнес-логики (сервис динамического ценообразования и сервис расчета оценки платформы) агент должен предлагать или писать unit-тесты (Jest).
Контекст: Перед выполнением любой задачи агент должен перечитать этот файл (@PROJECT_CONTEXT.md) и убедиться, что решение не противоречит описанным бизнес-правилам.
